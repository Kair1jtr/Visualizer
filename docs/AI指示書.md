# おすすめの手順

## ① ルール完全形式化

まずルールを完全に「プログラムが扱える形」にする。AIへ以下を整理させます：

- 入力として何が与えられるか
- 出力として何を出すのか
- 1回の操作で何が変化するか
- 操作できる回数・時間
- 勝敗・得点の決まり方
- 絶対にしてはいけない操作
- 問題の最大サイズ

ここではまだ「最強のアルゴリズムを考えて」と頼まないほうがよい。

## ② 小さい例を自分たちで作る

盤面が 4×4 しかない、要素が 5 個しかない、というような極端に小さい問題を作る。

「この状態から、どんな操作をすれば最適になる？」を人間と AI の両方で考える。

この段階で見えてくること：

- 全探索でいけるのか
- BFS / DFS が使えるのか
- DP が使えるのか
- 貪欲法で十分なのか
- ビームサーチが必要なのか
- 評価関数を作る必要があるのか

## ③ 「必ず最適解が分かる方法」をまず作る

非常に重要。「完全解」を作る：

```
問題
 ↓
全ての可能な手を試す
 ↓
全ての結果を比較
 ↓
本当に最適な答えを得る
```

本番では計算量が大きすぎて使えなくても構わない。これを正解判定器（オラクル）として使い、AI が考えたアルゴリズムが本当に正しい方向に進んでいるのかを大量の小問題で検証する。

## ④ AI には「アルゴリズム候補を複数出させる」

ここで初めて AI を積極的に使う。例：

「この問題について、①全探索 ②貪欲法 ③DFS ④BFS ⑤動的計画法 ⑥ビームサーチ ⑦モンテカルロ法 のどれが適用可能か比較してください」

**重要**：AI の回答をそのまま採用しない。代わりに「このアルゴリズムが失敗する反例を作ってください」と聞く。

## ⑤ 「評価関数」を徹底的に考える

競技部門では非常に重要。例：

- 「次の 1 手で一番点数が高くなる場所へ行く」だけでは、数手先を見ると損をする可能性

評価関数：

```
現在の得点 ＋ 数手先で得られそうな得点 − 将来的な損失
```

第 34 回競技部門では、将来獲得できる陣地の得点や実現可能性を「利得」として評価。

## ⑥ 自動対戦を作る

3 人チームならぜひやるべき。例：

```
アルゴリズムA
      VS
アルゴリズムB

1000 試合
   ↓
勝率・平均得点・処理時間を記録
```

さらに A vs B、A vs C、B vs C、A 改良版 vs B、のように大量に対戦させる。

結果：「なんとなく強そう」ではなく、A：勝率 63％ B：勝率 37％ のように比較できる。

## ⑦ 最後に「制限時間」を組み込む

アルゴリズムの強さだけでなく、本番時間内に計算が終わるかが極めて重要。例：

- 探索深さ 2 → 0.01 秒 → 弱い
- 探索深さ 4 → 0.2 秒 → 強い
- 探索深さ 6 → 8 秒 → さらに強い
- 探索深さ 8 → 45 秒 → 本番では使えない

→ 深さ 6 が実戦的

実際の競技では、探索・行動決定・データ送信までを制限時間内に終わらせるため、探索深度を決める設計が使われる。

# AI の使い方で特に気をつけてほしいこと

AI を「アルゴリズムを作ってもらう人」ではなく「非常に優秀な壁打ち相手」として使うのがおすすめ。

## 悪い使い方

```
この問題を解く最強の C++ プログラムを書いて。
```

もっともらしいコードが出てきても、アルゴリズム自体が間違っている可能性がある。

## 良い使い方

```
① この問題を数学的にモデル化してください。
↓
② 考えられるアルゴリズムを 10 種類挙げてください。
↓
③ それぞれの計算量を比較してください。
↓
④ このアルゴリズムが失敗する反例を探してください。
↓
⑤ 全探索による正解と比較するテストプログラムを設計してください。
↓
⑥ この評価関数の弱点を探してください。
↓
⑦ このアルゴリズムを 1000 種類のランダムケースで検証するコードを書いてください。
```

# この競技での当てはめ（数値・設計）

上記の手順を「ヘキサうどん」に具体的に当てはめたもの。ルール自体は
`docs/ルール説明書.md` を参照（ここでは重複させない）。

## 探索空間の見積り（③のオラクル設計に使う）

`daySteps` は `W+H`〜`(W+H)×4`。W=H=32 の最大構成では `daySteps` は最大
`(32+32)×4 = 256`。1エージェントの1日の行動列は、平地移動(2ステップ)想定で
最大128手 × 各7択（6方向+待機）≈ **7¹²⁸ ≈ 10¹⁰⁸**。エージェント数分の組み合わせ
まで考えると当然全探索は不可能。

→ **全探索によるオラクル（正解判定器）は極小ケース専用**として作る。目安:

| 用途 | 盤面 | エージェント | daySteps | 日数 | 概算 |
|---|---|---|---|---|---|
| オラクル | 4×4 | 1〜2機 | 6〜10 | 1〜2日 | 7⁵ ≈ 1.7万通り |
| 中規模検証 | 6×6 | 2機 | 12〜24 | 2日 | ビームサーチ等の比較用 |

## `revision` を使った anytime 提出（⑦の時間設計に使う）

行動計画は同じ日に何度でも再提出でき、`revision` が大きいものがより後に受理された
提出として扱われる（`POST /` のレスポンス `ActionAccepted.revision`）。これにより
「探索が間に合わず1日全損」という最悪ケースを構造的に回避できる:

```
1. 締切に対して十分早い段階で「必ず妥当な計画」を作って即提出（保険）
2. 残り時間で探索を深め、改善案ができるたびに再提出
3. 締切の手前で打ち切り（通信往復のマージンを確保）
```

対戦クライアントを作る際は、この3段構成を通信層に組み込むこと。
「まず安全な計画を即座に提出 → 時間が余る限り改善版を再提出」という設計が有効。

## 評価関数の重み付け（⑤に使う）

勝敗判定は ①種類数 → ②日ごとの種類数の累積 → ③玉数 → ④回答時間 の順
（`docs/ルール説明書.md` §14）。この優先順位から:

- 玉数より**系列の網羅が最優先**
- ②があるため「**早い日に多種類を揃える**」ほど累積が伸びる
  （最終日に全種類揃えても累積は1日分しか稼げない）
- → 評価関数は「新規系列 > 本日未取得系列 > 既取得系列」の重み付けが自然
  （`simulator/strategy.py` の `GreedyStrategy` がこの重み付けを実装している）
