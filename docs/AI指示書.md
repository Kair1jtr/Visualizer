# おすすめの手順

## ① ルール完全形式化

まずルールを完全に「プログラムが扱える形」にする。AIへ以下を整理させます：

- 入力として何が与えられるか
- 出力として何を出すのか
- 1回の操作で何が変化するか
- 操作できる回数・時間
- 勝敗・得点の決まり方
- 絶対にしてはいけない操作
- 問題の最大サイズ

ここではまだ「最強のアルゴリズムを考えて」と頼まないほうがよい。

## ② 小さい例を自分たちで作る

盤面が 4×4 しかない、要素が 5 個しかない、というような極端に小さい問題を作る。

「この状態から、どんな操作をすれば最適になる？」を人間と AI の両方で考える。

この段階で見えてくること：

- 全探索でいけるのか
- BFS / DFS が使えるのか
- DP が使えるのか
- 貪欲法で十分なのか
- ビームサーチが必要なのか
- 評価関数を作る必要があるのか

## ③ 「必ず最適解が分かる方法」をまず作る

非常に重要。「完全解」を作る：

```
問題
 ↓
全ての可能な手を試す
 ↓
全ての結果を比較
 ↓
本当に最適な答えを得る
```

本番では計算量が大きすぎて使えなくても構わない。これを正解判定器（オラクル）として使い、AI が考えたアルゴリズムが本当に正しい方向に進んでいるのかを大量の小問題で検証する。

## ④ AI には「アルゴリズム候補を複数出させる」

ここで初めて AI を積極的に使う。例：

「この問題について、①全探索 ②貪欲法 ③DFS ④BFS ⑤動的計画法 ⑥ビームサーチ ⑦モンテカルロ法 のどれが適用可能か比較してください」

**重要**：AI の回答をそのまま採用しない。代わりに「このアルゴリズムが失敗する反例を作ってください」と聞く。

## ⑤ 「評価関数」を徹底的に考える

競技部門では非常に重要。例：

- 「次の 1 手で一番点数が高くなる場所へ行く」だけでは、数手先を見ると損をする可能性

評価関数：

```
現在の得点 ＋ 数手先で得られそうな得点 − 将来的な損失
```

第 34 回競技部門では、将来獲得できる陣地の得点や実現可能性を「利得」として評価。

## ⑥ 自動対戦を作る

3 人チームならぜひやるべき。例：

```
アルゴリズムA
      VS
アルゴリズムB

1000 試合
   ↓
勝率・平均得点・処理時間を記録
```

さらに A vs B、A vs C、B vs C、A 改良版 vs B、のように大量に対戦させる。

結果：「なんとなく強そう」ではなく、A：勝率 63％ B：勝率 37％ のように比較できる。

## ⑦ 最後に「制限時間」を組み込む

アルゴリズムの強さだけでなく、本番時間内に計算が終わるかが極めて重要。例：

- 探索深さ 2 → 0.01 秒 → 弱い
- 探索深さ 4 → 0.2 秒 → 強い
- 探索深さ 6 → 8 秒 → さらに強い
- 探索深さ 8 → 45 秒 → 本番では使えない

→ 深さ 6 が実戦的

実際の競技では、探索・行動決定・データ送信までを制限時間内に終わらせるため、探索深度を決める設計が使われる。

# AI の使い方で特に気をつけてほしいこと

AI を「アルゴリズムを作ってもらう人」ではなく「非常に優秀な壁打ち相手」として使うのがおすすめ。

## 悪い使い方

```
この問題を解く最強の C++ プログラムを書いて。
```

もっともらしいコードが出てきても、アルゴリズム自体が間違っている可能性がある。

## 良い使い方

```
① この問題を数学的にモデル化してください。
↓
② 考えられるアルゴリズムを 10 種類挙げてください。
↓
③ それぞれの計算量を比較してください。
↓
④ このアルゴリズムが失敗する反例を探してください。
↓
⑤ 全探索による正解と比較するテストプログラムを設計してください。
↓
⑥ この評価関数の弱点を探してください。
↓
⑦ このアルゴリズムを 1000 種類のランダムケースで検証するコードを書いてください。
```

# 3 人チームなら、役割分担も重要

| 担当 | 主な仕事                         |
| ---- | -------------------------------- |
| A    | アルゴリズム・数学的考察         |
| B    | 実装・高速化                     |
| C    | テスト・ビジュアライザ・自動対戦 |

**注意**：3 人全員がアルゴリズムを理解するようにしてください。特に C++ コードを書ける人だけがアルゴリズムを理解している状態は危険。
