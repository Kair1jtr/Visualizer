## ① 入力として何が与えられるか

### A. 試合設定（試合開始前に1回）✅**API** `GET /setting` → `MatchSetting`

| キー | 型 | 意味 | 範囲・備考 |
|---|---|---|---|
| `startsAt` | int | 試合開始時刻(UNIX time) | **確定前は `0`** が返る ✅API |
| `daySeconds` | int[] | 各日の**回答時間(秒)** | 要素数=日数 |
| `daySteps` | int[] | 各日のステップ数 | **`W+H` 〜 `(W+H)×4`** ✅API |
| `map.height` / `map.width` | int | 盤面 H / W | |
| `map.cells` | int[H][W] | 地形 | `0`平地 `1`道路 `2`山地 `3`池 ✅設定 |
| `spots[]` | `{brand, pos, stocks}` | スポット | brand=系列, stocks=最大在庫量 |
| `agents[]` | int[] | 自分のエージェント初期位置 | **この順序が以降すべての基準** ✅書式 |
| `fuelLimits` | int | 燃料積載量上限 | **1日目ステップ数の1〜3倍** ✅API |
| `players` | int | 参加競技者数 | |
| `busyThreshold` | int | 混雑基準値 | **1〜5** ✅API |
| `jammedThreshold` | int | 渋滞基準値 | **2〜10** ✅API |

### B. 試合状態（各日の開始時）✅**API** `GET /` → `MatchState`

| キー | 意味 |
|---|---|
| `endsAt` | その日の**回答受付終了時刻**(UNIX time) |
| `day` | 日番号（初日は `0`） |
| `agents[]` | 自分のエージェント `{kind, pos, fuel}`。kind `0`巡回車 `1`補給車 |
| `others[]` | 他プレイヤー `{id, agents[]}` — **他チームの位置・燃料も全部見える** |
| `traffics[]` | `{pos, status}` status `0`順調 `1`混雑 `2`渋滞 |

### 座標系 ✅設定

セル番号は**行優先の1次元インデックス**。

```
pos = y * width + x
x   = pos % width
y   = pos / width
```

盤面は pointy-top の **odd-r offset**（奇数行が右に半セルずれる）hex グリッド。

## ② 出力として何を出すのか

### A. エージェント種別（試合開始前に1回）✅**API** `POST /agent`

```json
[0, 1, 0, 1]
```
`0`=巡回車, `1`=補給車。**要素数はエージェント数と一致必須**。

### B. 行動計画（毎日1回）✅**API** `POST /`

```json
[
  [-15],
  [0, 1, -10]
]
```

- 外側の配列＝エージェント（`setting.agents` と同じ順序）、内側＝そのエージェントの行動列
- `-1以下` = 待機（絶対値がステップ数）
- `0〜5` = 移動方向

| コード | 0 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|
| 方向 | 左上 | 右上 | 右 | 右下 | 左下 | 左 |

**レスポンス** `ActionAccepted.revision` ✅API:
- `0未満` = 提出失敗 / `0以上` = 受理
- **同じ日に複数回提出でき、`revision` が大きいものがより後に受理された提出**

> 💡 これは重要。**回答時間内なら何度でも出し直せる**ので、
> 「まず安全な計画を即座に提出 → 時間が余る限り改善版を再提出」という
> anytime アルゴリズムが有効（⑦参照）。

### 認証 ✅API

`Procon-Token` **ヘッダ**、または `token` **クエリパラメータ**でトークンを渡す。

## ③ 1回の操作で何が変化するか

### 構造的性質

これはリアルタイムゲームではなく、**1日分の行動列をまとめて事前提出する**方式。
解くべきは「1日分の行動列を決める最適化問題 × 日数」であり、
**日の途中で他チームの動きに反応することはできない**（日の開始時点の情報のみ）。

### 移動1回で起きること

| 変化 | 内容 |
|---|---|
| 消費ステップ | ⚠️ **出発セル（現在地）の地形**で決まる。到着先ではない ← 最も間違えやすい |
| 消費燃料 | 同じく出発セルの地形。⚠️ **巡回車のみ**消費、補給車は消費しない |
| 位置 | 消費ステップ数が経過して初めて到着（移動中は複数ステップ拘束される） |

**コスト表** ⚠️要再確認（募集要項 表1 由来。`visualizer/pathfinding.py:12`）

| 地形 | ステップ | 燃料 |
|---|---|---|
| 平地 | 2 | 1 |
| 山地 | 3 | 2 |
| 道路（順調） | 1 | 2 |
| 道路（混雑） | 2 | 2 |
| 道路（渋滞） | 4 | 2 |
| 池 | 進入不可 | — |

### 移動以外の状態変化 ⚠️要再確認

- **獲得**: 巡回車がスポットのセルに**到着した瞬間**、在庫>0 かつ「その巡回車がその日そのスポット未取得」なら1玉獲得。
  すでに居座っているセルでは発火しない（一度離れて戻る必要あり）
- **補給**: 巡回車と補給車が**同一セルに1ステップ以上一緒に留まる**と燃料が `fuelLimits` まで回復
- **交通量の記録**: 道路セルへの滞在ステップ数が累積され、翌日以降の道路状態に反映
- **在庫**: チームごとに独立（他チームが取っても自分の在庫は減らない）。毎日 `stocks` まで補充

### 道路状態の決定 ⚠️要再確認

```
volume = (前日 + 前々日の全チーム滞在ステップ数) ÷ 参加チーム数
volume >= jammedThreshold → 渋滞(2)
volume >= busyThreshold   → 混雑(1)
それ以外                   → 順調(0)
```
初日は全て順調。

### 状態遷移の実装モデル

1日をシミュレートするのに必要な状態:

```
各エージェント: 位置 / 燃料 / 移動中の残ステップ / 本日獲得済みスポット集合
チーム単位:     スポット在庫 / 獲得済み系列集合 / 本日獲得系列集合 / 玉数
盤面:           道路セルごとの滞在ステップ累積（翌日の道路状態用）
```

1ステップの進行順序（本リポジトリ `visualizer/hexaudon.py` の実装。⚠️順序の細部は要確認）:

1. 移動中でないエージェントが次の行動を取り出す
2. 移動開始 → 出発セルの地形からコスト決定、燃料を消費、移動中カウンタをセット
3. 道路セル滞在をカウント
4. 移動中カウンタを1減らし、0になったら到着 → スポットなら獲得判定
5. 補給判定（巡回車と補給車が1ステップ間ずっと同セルにいたか）

## ④ 操作できる回数・時間

| 制約 | 値 |
|---|---|
| 提出回数 | 種別1回 + 行動計画を1日1回（ただし**同じ日に再提出可**、最後の受理が有効）✅API |
| 1回の思考時間 | `daySeconds[day]` 秒 |
| 締切 | `endsAt`（絶対時刻）。通信往復も込みで間に合わせる |
| 1日の行動量 | `daySteps[day]` ステップ（`W+H` 〜 `(W+H)×4`）✅API |
| 種別提出の締切 | 簡易サーバーでは起動から既定 `5s`（`-kind-deadline`）、その後 `5s`（`-match-start-delay`）で試合開始 ✅簡易サーバーREADME |

**公式example**（`server/試合設定用JSONファイル/example.json`）: 10×10、`daySteps=[20,20,20,20]`、`daySeconds=[30,30,30,30]`、`fuelLimits=20`、エージェント3機、2チーム。

## ⑤ 勝敗・得点の決まり方 ⚠️要再確認

優先順位:

1. **うどんの種類数** — 全日程で獲得した `brand` の異なり数
2. **日ごとの種類数の累積** — 各日「その日獲った種類数」を全日分合計
3. **玉の総数**
4. 回答時間

**戦略的含意**:
- 玉数より**系列の網羅が最優先**
- ②があるため「**早い日に多種類を揃える**」ほど累積が伸びる
  （最終日に全種類揃えても累積は1日分しか稼げない）
- → 評価関数は「新規系列 > 本日未取得系列 > 既取得系列」の重み付けが自然

## ⑥ 絶対にしてはいけない操作（リジェクト条件）

### 公式に明記されている不正 ✅API / ✅書式

| 対象 | 不正条件 |
|---|---|
| 種別 | 要素数がエージェント数と不一致 / `{0,1}` 以外の値 |
| 行動計画 | **合計ステップ数がその日のステップ数と不一致** |
| 行動計画 | **移動できない方向への移動**（池・マップ外） |
| 行動計画 | 🔴 **必要燃料が不足する移動** ✅API |

### 特に重要な2点

- 🔴 **1つでも不正な行動が含まれる場合、全エージェントの行動計画を不正として扱う** ✅API
  （部分採用はされない）
- **リジェクト／時間切れ時のデフォルト** ✅書式
  - 種別 → **全エージェントが巡回車**になる
  - 行動計画 → **全エージェントが1日待機**（= その日を丸ごと失う、致命的）

### 実装上の必須対策

**提出前にローカルで完全検証する**こと。特に**燃料チェックは公式で不正条件なので必須**。
検証すべき項目:

1. 配列の要素数 == エージェント数
2. 各値が `-1以下` または `0〜5`
3. ステップ合計 == `daySteps[day]`（出発セル地形＋その日の道路状態で計算）
4. 全移動先が盤内かつ池でない
5. **各移動時点で燃料が足りている**（巡回車のみ、補給による回復も加味）

## ⑦ 問題の最大サイズと探索空間

| 項目 | 値 | 出典 |
|---|---|---|
| `daySteps` | `W+H` 〜 `(W+H)×4` | ✅API |
| `fuelLimits` | 1日目ステップ数の1〜3倍 | ✅API |
| `busyThreshold` | 1〜5 | ✅API |
| `jammedThreshold` | 2〜10 | ✅API |
| マップ W / H | ❌未確定（本リポジトリのモックは 8〜32 を仮定） | ❌ |
| エージェント数 | ❌未確定（モックは 3〜8 を仮定。公式exampleは3機） | ❌ |
| 日数 | ❌未確定（`daySteps` の配列長。モックは 4〜10、公式exampleは4日） | ❌ |
| 参加者数 | 公式exampleは2、フォーマット資料の例は8 | — |

### 探索空間の見積り

W=H=32 とすると `daySteps` は最大 `(32+32)×4 = 256`。
1エージェントの1日の行動列は、平地移動(2ステップ)想定で最大128手 × 各7択（6方向+待機）
≈ **7¹²⁸ ≈ 10¹⁰⁸**。エージェント数分の組み合わせまで考えると当然全探索は不可能。

→ **全探索によるオラクル（正解判定器）は極小ケース専用**として作る。目安:

| 用途 | 盤面 | エージェント | daySteps | 日数 | 概算 |
|---|---|---|---|---|---|
| オラクル | 4×4 | 1〜2機 | 6〜10 | 1〜2日 | 7⁵ ≈ 1.7万通り |
| 中規模検証 | 6×6 | 2機 | 12〜24 | 2日 | ビームサーチ等の比較用 |

### 時間設計（`daySeconds` への適合）

`revision` による**再提出が可能**なので、次の設計が有効:

```
1. 締切に対して十分早い段階で「必ず妥当な計画」を作って即提出（保険）
2. 残り時間で探索を深め、改善案ができるたびに再提出
3. 締切の手前で打ち切り（通信往復のマージンを確保）
```

これにより「探索が間に合わず1日全損」という最悪ケースを構造的に回避できる。
