## 2. 実装中に判明した仕様上の事実（実装指示書「最後に」への報告）

### 2.1 U-6（燃料消費タイミング）は〔補足〕から確定できる

**仕様書の記述**

状態設計書 第19章B は U-6 を【未確認】とし、
「複数ステップ移動での燃料消費タイミング（開始時1回か各ステップか）」を
実装前に公式へ確認すべき事項（優先度**高**）に挙げていた。

**現在の実装**

`policies.FuelTiming.ON_ARRIVAL` を既定とし、
**移動が完了する反映フェーズで全額を消費する**。

**疑問点と、それを解決した根拠**

〔補足〕の状態遷移表にある巡回車Aの燃料推移を追うと、選択肢が一つに絞られる。

巡回車A（初期セル0、行動計画 `2,2,2,-1`、最大燃料3）:

| ステップ | 出来事 | 燃料 |
|---|---|---|
| 0 | セル0（道路・順調）から移動を予約（所要1・燃料2） | 3 |
| 1 | 燃料消費 → 移動反映（セル1へ） | 3 → **1** |
| 1 | セル1（道路・混雑）から移動を予約（所要2・燃料2） | 1 |
| 2 | 補給車Aがセル1に到着 → 補給 | 1 → **3** |
| 3 | 燃料消費 → 移動反映（セル2へ） | 3 → **1** |
| 5 | 燃料消費 → 移動反映（セル3へ） | 1 → **0** |

ここで決定的なのは **ステップ1で予約した移動の燃料が、ステップ2ではなく
ステップ3（移動完了時）に消費されている**ことである。

- 「予約直後の反映フェーズ（ステップ2）で消費」だとすると、Aの燃料は1しかなく
  必要量2を満たせない。〔補足〕はAの行動計画を**有効**（唯一の注意点は
  「最後に待機を指定しないとエラーになる」こと）としているので、この解釈は成り立たない。
- 「アクションフェーズで消費」は〔Q6〕の「移動を予約、燃料は反映フェーズで消費」に反する。
- 残るのは **移動が完了する反映フェーズで消費** のみ。

**副次的に確定すること**

燃料充足の判定時点も同時に定まる。〔要項〕は
「燃料が足りない場合に移動の命令を与えた場合は，無効な回答となります」と述べるが、
上記より **判定は「移動が完了する時点で足りているか」** である
（予約時点ではないことが、巡回車Aの例から分かる）。
`validation.validate_team_plan()` はこの解釈で dry-run 検証している。

**検証**

`tests/test_official_supplement.py::test_fuel_consumed_on_arrival_not_on_reservation`
が巡回車Aの燃料イベント列 `[(1,消費),(2,補給),(3,消費),(5,消費)]` を突き合わせている。

**扱い**

実装指示書 第7章の指示に従い、U-6 は切り替え可能なまま残している
（`ON_FIRST_REFLECTION` / `ON_RESERVATION` も選べる）。既定のみ確定値に置いた。

### 2.2 状態設計書の設計判断から変更した点

**滞在ステップ数を道路セル以外でも記録する**

- 状態設計書 第9.3節は「道路セル以外の滞在も記録するか → **記録しない**【推定】」としていた。
- 実装では**全セルで記録**している。理由は、〔補足〕の滞在数の表が平地セル（セル2・3）も
  含めて示されており、**公式例との突き合わせに必要**なため（実装指示書 第8章が
  公式テストケースの再現を最優先としている）。
- 道路状態の判定には道路セルのみを使うので、**結果は変わらない**。
- これは【推定】どうしの差し替えであり、公式仕様の解釈を変えたものではない。

### 2.3 テストの期待値を修正した箇所（実装ではなく仕様理解の誤り）

実装指示書 第8章「仕様と実装のどちらが間違っているかを明確に切り分ける」への記録。

| 当初のテスト期待値 | 実際 | 判定 |
|---|---|---|
| 2日連続で別スポットを取ると日別種類数が `[1, 1]` | `[1, 2]` | **テストが誤り**。前日にスポットへ到着してそのまま日を終えると、翌日の1ステップ目にそのスポットを再獲得する〔Q7〕。〔補足〕巡回車Eと同じ挙動 |
| 順調な道路を渡ると出発セルに1回計上される | 到着セルに計上 | **テストが誤り**。順調な道路は1ステップなので「移動中」の期間が存在しない |
| 2チームの滞在合計が5 | 3 | **テストが誤り**。手計算のミス |

いずれも実装は仕様どおりで、テスト側を修正した。

## 3. パッケージ構成

```
simulator/
  policies.py     未確定仕様の切り替え（U-1/U-3/U-4/U-5/U-6）
  terrain.py      地形・道路状態・移動コスト表（〔要項〕表1）
  grid.py         セル番号・座標・隣接関係（U-1/U-2 の隔離場所）
  state.py        HexaUdon / TeamState / AgentState / SpotDef / TrafficState
                  （フィールド名は〔書式〕のJSONキーに合わせている。第7章参照）
  actions.py      行動計画の表現と展開
  validation.py   受付時検証（構造 → 歩行 → 燃料 dry-run）
  engine.py       反映フェーズ・アクションフェーズ・日・試合
  pathfinding.py  その日の道路状態を反映した Dijkstra（P-4 の解消）
  strategy.py     戦略クラス（Strategy / SpotScoreStrategy と参照実装4種）。
                  Param でパラメータを宣言でき、API・UI が自動でフォーム化する
  tracing.py      追跡ログとスナップショット
  scenarios.py    公式資料に載っている試合設定
  compare.py      戦略比較の実行基盤
visualizer/
  sim_spectator.py  観戦アダプタ。HexaUdon を spectator.py と同じ形の JSON に
                    変換する（P-5 の解消）。ルールは実装せず engine に委ねる
tests/
  test_official_supplement.py  〔補足〕の状態遷移例（19件）
  test_rules.py                ルール単体（42件）
  test_traffic.py              交通量・道路状態（10件）
  test_pathfinding.py          経路探索（8件）
  test_sim_spectator.py        参照戦略と観戦アダプタ（17件）
  test_strategy_classes.py     戦略クラス・パラメータ・継承（20件）
examples/
  simulator_demo.py            公式例の再生 / 戦略比較デモ
```

`simulator/` は通信も描画も含まない。`sim_spectator.py` を `visualizer/` 側に
置いているのは、状態設計書 第18.3節の層分け（第1層＝ルール、第2層＝入出力）を
崩さないためである。

### 状態の一元管理

`HexaUdon` を唯一の状態とし、「現在の状態」と「次のステップで発生するイベント」を
分けている（実装指示書 第3章）。

- **現在の状態**: `AgentState.pos` / `.fuel`、`TeamState.spot_stocks`、`TrafficState`
- **予約されたイベント**: `AgentState.reserved`（`ReservedAction`）

`reserved` はアクションフェーズで設定され、反映フェーズで消費される。
これにより「まだ起きていない移動」が位置や燃料に混ざらない。

## 6. 使い方

### ブラウザで観戦する

```bash
python app.py   # http://127.0.0.1:8000/sim.html を開いて「実行」
```

`simulator/` の試合を、公式簡易サーバーの観戦ビューと同じ盤面で表示する。
軌跡は推定ではなく実測で、ステップ単位で再生できる。詳細は README.md の
「シミュレーター観戦」を参照。

### 公式例を再生して追跡ログを見る

```bash
python examples/simulator_demo.py official
```

### 戦略を比較する

```bash
python examples/simulator_demo.py traffic
```

デモは「道路に居座る」場合と「道路を通り抜けてスポットに居座る」場合を4日間比較し、
前者では交通量が 0 → 7 → 15 → 16 と積み上がって道路が渋滞へ変化すること、
後者では順調のまま推移して毎日うどんを獲得できることを示す。

### 未確定仕様を切り替える

```python
from simulator.policies import Policies, TrafficDivision

policies = Policies(traffic_division=TrafficDivision.CEIL)
```

`policies.describe()` で採用中の仮仕様を一覧できる。

## 7. 既存コードとの関係

以前は `visualizer/hexaudon.py`（モックサーバー用シミュレーター）が併存しており、
公式と異なる意味論（燃料不足を「補給されるまで待機」として実行する）を持っていた。
**これは削除済み**で、競技ルールの実装は `simulator/` の1か所だけになった。

同時に、モックサーバーのエンドポイント（`/api/match` 系・`/api/live/*`）、
デバッグGUI（`/debug`）、旧ビジュアライザ（`/simulator.html`・`/watch.html`）も
削除した。`app.py` に残るのは観戦用の2系統だけである。

| | 内容 |
|---|---|
| `/api/real/*` | 公式簡易サーバー procon-server を起動して観戦（軌跡は推定） |
