## 1. 状態設計の目的

本設計の目的は次の一文に集約されます。

> **試合開始時に与えられる情報から初期状態を構築し、各ステップの
> アクションフェーズと反映フェーズを繰り返すことで、ヘキサうどんの試合状態を
> 正確に再現する。**

この目的のために必要な状態**のみ**を設計します。以下の方針を置きます。

| 方針 | 内容 |
|---|---|
| 最小性 | 他の状態から一意に計算できる値は、原則として状態に持たない（第15章で分類） |
| 忠実性 | 公式が定めた処理順序（第12章）を状態遷移としてそのまま表現できること |
| 分離 | 「競技ルール上存在する状態」と「シミュレーター実装の都合で必要な内部状態」を明確に分ける |
| 検証可能性 | 〔補足〕の状態遷移例を再現できること（第17章） |

### 1.1 本設計が対象とする範囲

| 範囲 | 対象か | 理由 |
|---|---|---|
| 盤面・エージェント・スポット・交通量の状態遷移 | ○ | 本設計の主題 |
| 行動計画の検証（受付時判定） | ○ | 状態遷移の前提条件であり、公式が処理順序を規定している〔Q6〕 |
| 得点・勝敗判定に必要な記録 | ○ | 第10章 |
| 回答時間の実時間計測 | △ | 測定基準が【未確認】のため、**外部から与えられる値**として扱う（第10章） |
| 通信プロトコル | × | シミュレーター本体の外側に置く（第18章） |
| マップのランダム生成 | × | 本設計では固定入力を前提とする（第17章） |

## 3. GameState

### 3.1 全体構造

```
GameState
├── config          ... 試合設定（不変）
│   ├── days, daySteps[], daySeconds[], startsAt
│   ├── fuelLimits
│   ├── busyThreshold, jammedThreshold
│   └── numTeams
├── map             ... MapState（不変。第4章）
├── spots           ... スポットの静的定義（不変。第5章）
├── teams[]         ... TeamState の配列（可変。第6章）
├── traffic         ... TrafficState（可変。第9章）
├── day             ... 現在の日（0始まり）
└── step            ... 現在のステップ
```

### 3.2 GameState に保持すべきもの／別 State に分けるべきもの

| 情報 | 配置 | 理由 | 確定度 |
|---|---|---|---|
| 試合設定（日数・ステップ数・閾値・燃料上限） | GameState 直下 | 試合を通じて不変。全 State から参照される 〔書式〕 | 【確定】 |
| マップ（高さ・幅・地形） | MapState | 試合中不変〔要項〕。地形は全チーム共通で1つだけ持てばよい | 【確定】 |
| **道路の状態（順調/混雑/渋滞）** | **TrafficState**（MapState ではない） | 地形と異なり**日ごとに変化する**〔要項〕。不変のマップ定義とは寿命が違うため分離する | 【確定】（変化すること）／【推定】（分離という設計判断） |
| スポットの位置・系列・最大在庫 | GameState 直下（静的定義） | 試合中不変〔要項〕。全チームで共通の定義 | 【確定】 |
| **スポットの現在在庫** | **TeamState**（スポット定義ではない） | 在庫は**チームごとに独立**〔要項〕。スポット側に持つとチーム分の多重化が必要になり不自然 | 【確定】（独立性）／【推定】（配置という設計判断） |
| エージェントの位置・燃料 | AgentState（TeamState 配下） | チームに属する〔要項〕 | 【確定】 |
| 交通量（滞在ステップ数の履歴） | TrafficState | **全チーム分を合算**して用いる〔要項〕ため、チームをまたぐ集約が必要 | 【確定】 |
| 現在の日・ステップ | GameState 直下 | 全 State に共通の進行位置 | 【推定】（内部表現） |
| 得点（種類数・玉数など） | TeamState | チームごとの記録〔要項〕 | 【確定】 |

### 3.3 「現在の日」「現在のステップ」の位置づけ

- 「日」と「ステップ」という時間単位の存在は【確定】〔要項〕。
- 日は0始まり【確定】〔書式〕（`day` キー、初日は0）。
- 「現在ステップを GameState のフィールドとして持つ」ことは公式が定めた仕様ではなく、
  シミュレーターの内部表現である → 【推定】。

- 〔要項〕本文には並び順の記述がなく、図1（画像）に委ねられている。本作業環境では

### 4.5 六方向の隣接関係 ― Claude Code が推測した内容

> **本節の内容を確定仕様として扱わないでください。**

第4.3節の番号割り当て規則（行優先）を前提として初めて、セル番号どうしの
隣接関係を式で表せます。前提が【未確認】である以上、以下も【推定】です。

| 方向コード | 偶数行（右にずれる行）から | 奇数行から | 確定度 |
|---|---|---|---|
| 0（左上） | `(r-1, c)` | `(r-1, c-1)` | 【推定】 |
| 1（右上） | `(r-1, c+1)` | `(r-1, c)` | 【推定】 |
| 2（右） | `(r, c+1)` | `(r, c+1)` | 【推定】 |
| 3（右下） | `(r+1, c+1)` | `(r+1, c)` | 【推定】 |
| 4（左下） | `(r+1, c)` | `(r+1, c-1)` | 【推定】 |
| 5（左） | `(r, c-1)` | `(r, c-1)` | 【推定】 |

（`r` = 行, `c` = 列。算出結果が盤外なら移動不可）

**設計上の指針**: 隣接関係は MapState 内部の**単一の導出関数**に閉じ込め、
他の State から直接インデックス計算を行わない構造とします。番号割り当て規則が
公式に確定した際、この1か所の修正のみで全体が追随できるようにするためです。
（この方針自体は設計判断であり【推定】）

### 5.3 「同一巡回車・同一スポット・同一日に1玉まで」を再現するために必要な状態

公式ルール:

> 1巡回車が1スポットから1日に獲得できるうどんの数は1玉まで。同じ日に同じ巡回車が
> 同じスポットを何度訪れても、獲得できるのは初回に訪れたときのみ。〔要項〕【確定】

このルールは**在庫だけでは再現できません**。在庫はチーム単位の値であり、
「どの巡回車が取ったか」を区別しないためです。したがって次の状態が必要です。

| 必要な状態 | 粒度 | 型 | リセット時期 | 確定度 |
|---|---|---|---|---|
| **当日取得済みスポット集合** | **巡回車1体ごと** | セル番号（またはスポットID）の集合 | **各日の開始時に空へリセット** | 【推定】 |

- ルールの存在は【確定】ですが、「巡回車ごとに集合を持つ」という**表現方法**は
  公式が規定したものではないため【推定】とします。
- 日が変われば再び獲得できる〔要項〕〔Q8〕〔Q17〕【確定】ため、日開始時のリセットは必須です。
- 保持粒度は「巡回車ごと」で十分です。理由: 判定条件が
  「その巡回車が・その日・そのスポットから取得済みか」の1点のみであり、
  チーム単位・スポット単位の集約では巡回車を区別できないためです。

**判定式（概念）**:
```
獲得できる ⇔ (現在地がスポット)
           ∧ (そのチームのそのスポットの在庫 > 0)
           ∧ (その巡回車の当日取得済み集合に そのスポットが含まれない)
```
各条件の根拠: 順に〔要項〕【確定】、〔要項〕【確定】、〔要項〕【確定】。

### 7.2 「移動中のエージェント」の表現

公式が定めている事実:

| 事実 | 根拠 | 確定度 |
|---|---|---|
| 移動命令を受けたエージェントは、**現在地の地形に割り当てられたステップ数の経過後**に次のセルへ移動する | 〔要項〕 | 【確定】 |
| アクションフェーズは「次のアクション（移動 or 待機）の**反映の予約**」を行う | 〔Q6〕〔補足〕 | 【確定】 |
| 移動を予約した時点では燃料を消費せず、**燃料消費は次の反映フェーズ**で行われる | 〔Q6〕〔補足〕 | 【確定】 |
| 移動が完了するまでの間に別の移動命令を出すことはできない | 〔Q23〕〔Q24〕 | 【確定】 |
| **移動中のエージェントは、移動が完了するまで出発セルに滞在しているものとして数えられる** | 〔補足〕滞在数（検証結果は第7.3節） | 【確定】 |

〔補足〕の状態遷移表には「予約行動」という列が存在し、`RT2`（ステップ2で右に移動）
`WT2`（ステップ2まで待機）のような表記で予約内容が記録されています〔補足〕【確定】。

以上より、移動中を表現するために必要な内部状態は次の通りです。

| 項目 | データ型 | 内容 | 確定度 |
|---|---|---|---|
| 予約中の行動 | 列挙（移動 / 待機 / なし） | アクションフェーズで設定 | 【推定】 |
| 移動先セル | 整数 or なし | 移動予約時に確定（出発セルと方向から決まる） | 【推定】 |
| 残り移動ステップ数 | 整数 | 反映フェーズごとに減算し、0で到着 | 【推定】 |

> **これらは公式が規定した状態名ではありません。**〔要項〕の
> 「割り当てられたステップ数の経過後に移動する」という規定を再現するには
> 経過を数える何らかの内部状態が必要である、という帰結として導いたものです。
> したがって【推定】に分類し、**公式仕様として扱いません**。

**代替表現の検討**: 「移動先＋残りステップ」の代わりに「行動計画の消化位置＋
その行動の開始ステップ」を持つ表現も考えられます。前者を採る理由は、
反映フェーズの処理（第12章）が「残りステップを1減らし、0なら移動を反映する」という
逐次処理として素直に表現でき、〔補足〕の遷移表と1対1で対応させやすいためです。
これは設計判断であり【推定】です。

### 7.3 「移動中は出発セルに滞在」の検証

〔補足〕の状態遷移表に記載された滞在数（累積値）を用いて検証しました。

- 条件: 1日6ステップ、エージェント8体（巡回車A〜G＋補給車A）〔補足〕
- 滞在数の最終累積の総和 = 12 + 17 + 12 + 7 = **48**
- エージェント数 × ステップ数 = 8 × 6 = **48**（一致）
- 各ステップの増分は常に **8**（＝エージェント数）

| 導かれる事実 | 確定度 |
|---|---|
| 各反映フェーズで、**全エージェントがちょうど1つのセルに滞在としてカウントされる** | 【確定】 |
| 複数ステップを要する移動の途中にあるエージェントも、**出発セル**でカウントされる | 【確定】 |
| **補給車も**滞在数のカウント対象に含まれる | 【確定】 |
| カウントは反映フェーズ（ステップ1〜N）で行われ、0ステップ目には行われない | 〔Q27〕〔補足〕【確定】 |

> 具体例（ステップ1時点）: 巡回車E は平地セル2から2ステップの移動中で未到着だが
> セル2にカウントされ、補給車Aも同じくセル2にカウントされている（セル2の増分＝2）。〔補足〕

### 9.3 設計上の判断とその根拠

| 論点 | 判断 | 理由 | 確定度 |
|---|---|---|---|
| 交通量そのものを保存するか | **保存しない** | 交通量は「(前日+前々日の滞在ステップ数) ÷ チーム数」で**一意に計算できる**〔要項〕。保存すると二重管理になる | 【推定】 |
| 何日分の滞在ステップ数を保存するか | **直近2日分＋当日分の計3枠** | 判定に必要なのは前日と前々日のみ〔要項〕。それ以前は参照されない | 【推定】 |
| 道路状態をいつ決定するか | **各日の開始時に1回** | 「各日の開始時に提供され、同一日中に変化しない」〔要項〕【確定】 |
| 道路状態を保存するか、都度計算するか | **保存する** | 日中不変〔要項〕であり、移動コスト計算で頻繁に参照されるため | 【推定】 |
| 道路セル以外の滞在も記録するか | **記録しない** | 交通量の定義が「各**道路**セルにおける」〔要項〕であり、他の地形は判定に使われない | 【推定】 |

### 18.1 簡易サーバーについて資料から確認できること

| 内容 | 根拠 | 確定度 |
|---|---|---|
| 「競技者向け**動作確認**サーバー」と明記されている | 〔簡易〕 | 【補助資料】 |

### 18.2 簡易サーバーの既定値を本番仕様として扱わないこと

> 〔簡易〕は自身を「**動作確認**サーバー」と明記しています【補助資料】。
> したがって `-kind-deadline 5s` および `-match-start-delay 5s` は
> **動作確認用の既定値**であり、**本番競技の種別決定時間・試合開始時間として
> 扱ってはなりません**。
>
> なお本番の想定時間については、公式Q&Aに「エージェントのタイプを指定する
> フェーズの解答時間は1分程度」〔Q4〕、「日毎の解答時間は1分程度」〔Q5〕という
> 記述があり、いずれも「詳細については本選実施要項で連絡」とされています【確定】。
> **確定値ではないため、シミュレーターに固定してはなりません** → 【未確認】。

### 18.3 3層構造の提案

```
┌─────────────────────────────────────────┐
│ 第1層  シミュレーター本体                                  │
│   ・GameState / MapState / TeamState / AgentState など     │
│   ・validate（回答検証）と simulate（状態遷移）            │
│   ・入力: simulation_input と day_input（第16章）          │
│   ・通信を一切含まない                                     │
│   ・実時間に依存しない（ステップ数のみで進行）             │
└─────────────────────────────────────────┘
                     ▲
                     │ 状態と行動計画の受け渡し（プロセス内）
                     ▼
┌─────────────────────────────────────────┐
│ 第2層  通信クライアント（アダプタ）                        │
│   ・外部サーバーの応答 → simulation_input / day_input へ変換│
│   ・行動計画 → 外部サーバーへの送信形式へ変換              │
│   ・実時間の締切管理（endsAt まで待つ等）はここに閉じる    │
│   ・認証・再提出などプロトコル固有の事情もここに閉じる     │
└─────────────────────────────────────────┘
                     ▲
                     │ HTTP
                     ▼
┌─────────────────────────────────────────┐
│ 第3層  サーバー                                            │
│   ・本番競技サーバー                                       │
│   ・公式配布の簡易サーバー（動作確認用）〔簡易〕           │
│   ・第1層のシミュレーターをサーバー化したもの（任意）      │
└─────────────────────────────────────────┘
```

### 18.4 この構造を採る理由

| 理由 | 説明 | 確定度 |
|---|---|---|
| 未確認事項の隔離 | 回答時間の測定基準【未確認】と通信プロトコルは第2層に閉じ込められ、第1層の状態設計に影響しない | 【推定】 |
| 検証の独立性 | 第1層は〔補足〕の状態遷移例（第17.2節）だけで検証でき、サーバーを必要としない | 【推定】 |
| 差し替え可能性 | 第3層を簡易サーバーから本番サーバーへ差し替えても、第1層は変更不要 | 【推定】 |

> **注意**: 簡易サーバーが実装している具体的な API エンドポイントや
> リクエスト／レスポンス形式は〔簡易〕〔CRED〕には記載がありません【補助資料】。
> 通信仕様は別途〔API〕に記載がありますが、これは公式ルール文書ではないため、
> 第2層の設計根拠としてのみ用い、**第1層の状態設計には持ち込みません**。

### F. 実装開始前に公式へ確認すべき事項

状態設計に影響する未確認事項に限って列挙します。

| 優先度 | # | 確認事項 | 影響 |
|---|---|---|---|
| **高** | U-1 | セル番号の割り当て規則。〔要項〕図1の内容、または本文での明文化 | **全移動処理の前提**。誤ると盤面全体が破綻する |
| **高** | U-3 | 交通量の「チーム数で割った値」は整数除算か。切り捨て／切り上げ／四捨五入のいずれか | 道路状態の判定が境界値で変わり、移動コストが変わる |
| **高** | U-6 | 複数ステップを要する移動で、燃料は移動開始時に1回消費されるのか、各ステップで消費されるのか | 巡回車の燃料推移。回答の有効／無効判定に直結する |
| **中** | U-5 | 移動反映のエージェント間の順序を決める規則。〔Q26〕のID順が移動反映にも適用されるか | 補給の成否（追走時）に影響する |
| **中** | U-4 | 2日目の交通量で、除数はチーム数のままか | 2日目の道路状態 |
| **中** | U-9 | 全チームのエージェント数は必ず同一か | TeamState の構造、交通量の合算 |
| **低** | U-8 | 補給車の `fuel` 値の意味（〔書式〕の例には20が入っている） | AgentState の表現のみ。挙動には影響しない見込み |
| **低** | U-12 | 失格・棄権が出た場合の交通量の除数 | 例外時のみ |
| **対象外** | U-7 | 回答時間の計測基準 | 第2層に隔離済み。第1層の状態設計には影響しない |
| **対象外** | U-10, U-11 | 対戦チーム数の上限、本番の各種制限時間 | 入力値として与えるため、状態設計には影響しない |

> **U-1 の補足**: 〔設定〕には行優先（`pos = y×width + x`）と明記されており【補助資料】、
> 実装上はこれを採用するのが妥当と考えられます。ただし〔設定〕は簡易サーバーの
> 設定ファイル形式の説明であり競技ルール文書ではないため、**公式仕様としては
> 未確認のまま**とし、第4.5節の方針どおり導出処理を1か所に閉じ込めます。

#### G-2. 公式確認を待った方がよい部分

| 範囲 | 理由 | 暫定的な進め方 |
|---|---|---|
| セル番号 ↔ 座標 ↔ 隣接関係の変換（U-1, U-2） | 全移動処理の前提が未確認 | 導出処理を**単一箇所に閉じ込め**、〔設定〕の行優先を暫定採用する。確定時にその1か所のみ差し替える |
| 交通量から道路状態を決める最終計算（U-3, U-4） | 除算の扱いで境界の判定が変わる | 除算方式を**切り替え可能なパラメータ**として設計し、確定後に固定する |
| 複数ステップ移動での燃料消費タイミング（U-6） | 燃料推移と回答の有効性に直結 | 〔補足〕の遷移表（テストケースA）を再現できる方を採用し、根拠を記録する |
| 移動反映の順序規則（U-5） | 追走時の補給成否に影響 | 順序を明示的に固定し、**どの順序を採用したかを記録**しておく |
| 回答時間の扱い（U-7） | 計測基準が未確認 | シミュレーター本体には持ち込まず、**外部入力**とする（第10.3節・第18.3節） |

#### G-3. 結論

- 第A節の確定状態のみで、**GameState の骨格・フェーズ構成・状態遷移の大部分は
  確定して実装に進めます**。
- 一方、**U-1（セル番号の割り当て規則）、U-3（除算の扱い）、U-6（燃料消費の
  タイミング）の3点は、誤ると試合結果そのものが変わる**ため、
  実装を進める場合も**該当箇所を差し替え可能な形に隔離**することを前提とします。
- 第17.2節のテストケースA（〔補足〕の公式状態遷移例）は、U-6 の判別と
  実装全体の検証を同時に行える最良の基準であり、**最初に着手すべき検証対象**です。
