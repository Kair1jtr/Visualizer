## 2. シミュレーター観戦ビュー（`/sim.html`）の新規実装

### 2.1 背景

これまで「公式ルール忠実シミュレーター（`simulator/`）」と「公式簡易サーバーの
観戦ビュー（`/`）」が別々に存在し、シミュレーターの結果を目で確認する手段が
テキストログしか無かった（`docs/report/実装報告書0826.md` P-5 の指摘）。

### 2.2 実装したもの

| ファイル | 役割 |
|---|---|
| `simulator/pathfinding.py` | その日の道路状態を反映した六角グリッド上の Dijkstra |
| `visualizer/sim_spectator.py` | `GameState` を観戦用JSONに変換する層。ルールは実装せず記録のみ行う |
| `app.py` の `/api/sim/*` | シミュレーターで1試合を実行し観戦データを返すAPI |
| `static/js/matchview.js` | 観戦ビューの描画本体（本番観戦とシミュレーター観戦で共用） |
| `static/js/realmatch.js` / `simmatch.js` | matchview への薄い結線 |
| `static/sim.html` | シミュレーター観戦ページ |

`visualizer/sim_spectator.py` は、公式簡易サーバー観戦用の `spectator.py` と
**同じ形のJSON** を返すことを設計上の制約にした。そのためブラウザ側は描画
コードを共有でき、両者の違いは次の3点のみになっている。

| | 本番試合観戦 `/` | シミュレーター観戦 `/sim.html` |
|---|---|---|
| 盤面を動かすもの | `procon-server` | `simulator/` |
| 移動軌跡 | 推定（2点間をDijkstraで補間） | 実測（全ステップの状態を保持） |
| 途中経過 | 見られない | ステップ単位で再生できる（スライダー・▶再生） |

`sim_spectator.py` はルールを一切持たず、状態遷移はすべて `simulator.engine`
に委任している（`docs/状態設計書.md` 第18.3節の層分けを維持）。

## 3. 戦略クラス階層とパラメータ調整GUI

### 3.1 要件

「プレイヤーごとに戦略とパラメータを個別設定できるようにしたい」
「戦略ボタンを押すとページ遷移なしでGUIが開くようにしたい」
「戦略クラスを作成して継承して使えるようにしたい」という3点の指示に対応した。

### 3.2 実装したもの

`simulator/strategy.py` に以下のクラス階層を作った。

```
Strategy                 基底。plan() を実装すれば戦略になる
 └ SpotScoreStrategy     「スポットを評価して高い順に回る」型の共通部分
    ├ GreedyStrategy     貪欲法
    │  └ BrandFirstStrategy   重みの既定値だけ変えた派生
    └ NearestStrategy    最近傍
 └ StayStrategy          plan() ごと上書きした例（比較の基準線）
```

継承先は `score_spot()` だけを実装すればよく、歩き方（ステップ数計算・燃料管理）
と補給車の動きは基底クラスが持つ。パラメータは `Param(name, label, kind,
default, minimum, maximum, ...)` で宣言し、`@register` を付けるだけで
`GET /api/sim/strategies` のスキーマとブラウザのフォームに自動反映される
（`app.py` もJavaScriptも修正不要）。

`static/js/simmatch.js` にプレイヤーごとの戦略設定を担当させ、`<dialog>` 要素
（`showModal()`）でページ遷移せずに戦略選択とパラメータ調整ができるようにした。
実行時は `POST /api/sim/start` にJSONボディで
`{"players": [{"strategy": "greedy", "params": {...}}, ...]}` の形で送る。

### 3.3 検証

`tests/test_strategy_classes.py`（20件）で、パラメータの型変換・範囲検査、
継承で既定値だけが変わること、新しいサブクラスを定義して `score_spot()` だけ
書いた戦略が公式の受付時検証を通ること、を確認した。

## 4. 発生した不具合と対応

### 4.1 `strict` 引数のエラー

作業途中で他コミット（`2a249ec`「既存実装の整合検証と、発見した4件の欠陥の
修正」）が `simulator/engine.py` の `reflection_phase` / `action_phase` /
`simulate_day_steps` から `strict` 引数を削除した。これにより
`visualizer/sim_spectator.py` が `strict=False` を渡していた箇所で
`TypeError` が発生し、`/api/sim/start` が 500 エラーになった。

`strict` の削除は「検証を省いて実行すると不正な計画が黙って別の意味に
解釈される」欠陥4件を修正する意図的な変更だったため、`sim_spectator.py`
側の `strict=False` を単純に削除して対応した。観戦アダプタは実行前に
必ず `validation.validate_all()` を通し、リジェクトされたチームは
全員待機のフォールバックに差し替えてから走らせているため、engine 側は
常に有効な計画しか受け取らない。厳格モードで問題ないことを確認した。
