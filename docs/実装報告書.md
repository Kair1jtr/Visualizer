## 1. 実装内容

### 1.1 何を作ったか

公式資料に書かれた状態遷移を**そのまま再現する**シミュレーターを新規に実装した。
既存の `visualizer/hexaudon.py`（モックサーバー用）とは別物であり、
本番の戦略検討に使うことを目的とする。

### 1.2 中核: 処理順序の厳密な再現

〔Q6〕〔補足〕で確定している順序を、そのままコードの構造にした。

```
0 step      : アクションフェーズのみ
1..N-1 step : 反映フェーズ → アクションフェーズ
N step      : 反映フェーズのみ

反映フェーズ（順序の入れ替え禁止）
  1. 燃料の消費        engine.reflection_phase() ①
  2. 移動の反映                                  ②
  3. うどんの獲得                                ③
  4. 燃料の補給                                  ④
  5. 交通量の更新                                ⑤
```

`simulate_day_steps()` が `for step in range(N+1)` で
`if step > 0: reflection` / `if step < N: action` を回す形になっており、
境界条件がコード上で1か所に見えるようにしてある。

### 1.3 設計上の要点

| 要点 | 内容 |
|---|---|
| **状態の一元管理** | `GameState` が唯一の状態。「現在の状態」（位置・燃料・在庫）と「予約されたイベント」（`AgentState.reserved`）を型で分離し、未実行の移動が現在位置に混ざらないようにした |
| **未確定仕様の集約** | U-1／U-3／U-4／U-5／U-6 を `policies.py` に集め、判断の実体は各1関数に閉じた。同じ判断をコードの複数箇所に書いていない |
| **検証と実行の分離** | 〔Q6〕「回答受付時に判定し、各ステップではすべての移動が可能な前提で進行」に対応して `validation.py` と `engine.py` を分けた |
| **追跡可能性** | `tracing.Tracer` が反映フェーズの各処理の変化を記録し、「このステップでなぜこの状態になったか」を後から追える |
| **戦略比較** | `compare.py` が同一初期状態から複数の行動計画を走らせ、日ごとの道路状態・交通量・得点を並べる |

### 1.4 交通量の多日伝播

実装指示書 第6章の要求（今日の判断が翌日・翌々日にどう効くか）に対応する。

- `TrafficState` が **当日／前日／前々日**の滞在ステップ数を全チーム合算で保持する
- 交通量そのものは保持せず `(前日 + 前々日) ÷ チーム数` で導出する
- 道路状態は日開始時に1回だけ決定し、日中は不変（〔要項〕）

デモ（`examples/simulator_demo.py traffic`）での実測:

| 日 | 道路に居座る戦略 | | 通り抜ける戦略 | |
|---|---|---|---|---|
| | 交通量 | 道路状態 | 交通量 | 道路状態 |
| 1日目 | 0 | 順調 | 0 | 順調 |
| 2日目 | 7 | **渋滞** | 1 | 順調 |
| 3日目 | 15 | **渋滞** | 1 | 順調 |
| 4日目 | 16 | **渋滞** | 0 | 順調 |
| 最終得点 | 種類0 累積0 玉0 | | 種類1 累積4 玉4 | |

### 5.3 解決した未確定事項

**U-6（燃料消費タイミング）は〔補足〕から確定できた。**

状態設計書では優先度**高**の未確認事項だったが、巡回車Aの燃料推移が選択肢を一つに絞る。

```
step0: セル0(道路・順調)から移動を予約（所要1・燃料2）    燃料 3
step1: 燃料消費 → 移動反映（セル1へ）                     燃料 3 → 1
step1: セル1(道路・混雑)から移動を予約（所要2・燃料2）    燃料 1  ← 必要量2に足りない
step2: 補給車Aがセル1に到着 → 補給                        燃料 1 → 3
step3: 燃料消費 → 移動反映（セル2へ）                     燃料 3 → 1  ← ここで消費
```

- 「予約直後（step2）に消費」だと燃料1で必要量2を満たせず、
  〔補足〕が**有効**としているAの行動計画が不正になってしまう
- 「アクションフェーズで消費」は〔Q6〕の「燃料は反映フェーズで消費」に反する
- 残るのは **移動が完了する反映フェーズで消費** のみ

**副次的に、燃料充足の判定時点も「移動完了時」だと確定する**
（予約時点ではない）。`validation.py` はこの解釈で検証している。

実装指示書 第7章の指示に従い切り替えは残したまま、既定を確定値に置いた。

## 6. 問題点

実装後に残っている課題。**優先度は「本番の戦略検討に支障が出る度合い」で付けた。**

### P-1【最優先】U-1（セル番号の割り当て）が未検証のまま

- **内容**: 行優先（`pos = y*width + x`）を採用しているが、根拠は〔設定〕（簡易サーバー付属の補助資料）のみ。公式競技資料には規則の記述がない。
- **影響**: 誤っていると**全移動処理・全隣接判定が破綻する**。盤面全体が無意味になる。
- **現状の緩和**: `grid.py` の `to_rc()` / `to_cell()` の2メソッドにのみ閉じ込めてあり、確定時はここだけ直せばよい。
- **必要な対応**: 〔要項〕図1の確認、または実機（簡易サーバー）で斜め移動を1回実行して結果セルを観測する。

### P-2【高】検証コストが実行の約11倍

- **内容**: `validate_team_plan()` が `GameState.clone()`（deepcopy）＋1日分の完全な dry-run を、**チームごと・日ごと**に実行する。
- **実測**: 公式最大規模で 1試合 2.23秒（検証込み）に対し、実行のみなら 0.20秒。8チーム×10日＝80回の dry-run が支配的。
- **なぜ dry-run が要るか**: 燃料充足の判定が**同一チーム内の補給**に依存するため、行動計画単独では判定できない。
- **影響**: ビームサーチやモンテカルロのように試合を何千回も回す探索では、この11倍が効いてくる。
- **緩和策（実装済み）**: `run_day(..., validate=False)` または `simulate_day_steps()` を直接呼べば検証を省ける。**戦略が有効な計画しか生成しないなら、探索中は検証を切ってよい。**
- **今後の改善案**: 燃料の逐次判定（dry-run を伴わない前方チェック）、`clone()` の軽量化（必要な状態だけコピー）。

### P-3【中】旧シミュレーターとの二重管理

- **内容**: `visualizer/hexaudon.py` が **公式と異なる意味論**のまま残っている。特に燃料不足を「補給されるまで待機」として実行する（`hexaudon.py:397`）が、公式は**回答全体をリジェクト**する〔要項〕〔Q6〕。
- **なぜ残しているか**: モックサーバー機能（`/api/*`）とWebビジュアライザが依存しているため。
- **影響**: 同一リポジトリに挙動の異なるシミュレーターが2つある。どちらの結果を見ているか取り違えると誤った戦略判断につながる。
- **対応案**: (a) `visualizer/hexaudon.py` を `simulator/` で置き換える、(b) 旧側を「モック専用・公式非準拠」と明示して用途を分離する。現状は (b) を `docs/実装ノート.md` 第7章に記載しているのみ。

### P-4【中】経路探索が無く、戦略を書くのが難しい

- **内容**: 戦略は方向コードの列を自分で組み立てる必要がある。`compare.straight_line_directions()` は**1行マップ専用**の簡易版。
- **影響**: 実際の 32×32 マップで「スポットへ向かう」戦略を書くには、その日の道路状態を反映した六角グリッド上の経路探索が必須。現状これが無い。
- **補足**: `visualizer/pathfinding.py` に Dijkstra があるが、旧 `visualizer/hexgrid` と旧コスト表現に結合しており、そのままでは `simulator/` から使えない。
- **対応案**: `simulator/` 側に、その日の道路状態を渡して最短経路を返す関数を追加する。

### P-5【中】`simulator/` の結果を Web ビジュアライザで見られない

- **内容**: `static/` の可視化は `visualizer/hexaudon.py` の出力形式（`hexaudon-official-v1`）に依存しており、`simulator/` の `GameState` を受け付けない。
- **影響**: 状態遷移を目で確認する手段が `tracing.snapshot()` / `map_ascii()` のテキストのみ。多数エージェント・大マップでは追いにくい。
- **対応案**: `GameState` の履歴を `hexaudon-official-v1` 形式に書き出すアダプタを作る。

### P-6【低】公式テストケースが六角の隣接関係を検証できない

- **内容**: 〔補足〕の状態遷移例は**セル0〜3が一直線**の図で、使う方向コードは `2`（右）と `5`（左）のみ。
- **影響**: 方向コード `0`（左上）`1`（右上）`3`（右下）`4`（左下）と、行の偶奇によるずれは、**公式例では一度も検証されていない**。現状は自己整合性テスト（対称性・往復・ルール説明書の表との一致）のみ。
- **P-1 との関係**: U-1 が確定していない以上、この部分は二重に未検証である。
- **対応案**: 簡易サーバーで斜め移動を実行し、実測で確認する。

### P-7【低】`compare.build_plan()` が燃料を考慮しない

- **内容**: その日の道路状態でステップ数は計算するが、燃料残量は見ない。
- **影響**: 燃料が厳しい設定でこのヘルパーを使うと、生成された計画が検証で弾かれる。
- **緩和**: docstring に明記済み。デモでは `fuel_limits=999` として燃料を論点から外している。

### P-8【低】戦略探索には性能が不足する可能性

- **内容**: 検証を切っても公式最大規模で 1試合あたり約0.2秒（= 毎秒5試合）。
- **影響**: 大規模なビームサーチ・モンテカルロには不足する見込み。
- **対応案**: 必要になった時点でプロファイルを取る。`reflection_phase()` の毎ステップのループ（エージェント数 × 5処理）と `ordered_agents()` の毎回のソートが主な候補。
