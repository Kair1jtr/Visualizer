## 1. 競技の概要

プレイヤーは「巡回車」と「補給車」の2種類のエージェントを操作し、六角形のセルで
構成された「マップ」上を移動します。マップ各地の「スポット」に巡回車が到着すると
うどんを獲得でき、補給車は巡回車に燃料を補給します。効率よくスポットを巡り、
**多くの種類のうどんを獲得したチームが勝利**します。【要項】

1試合は複数チームで同時に行われます。対戦チーム数は組み合わせによって異なります。【要項】

## 2. 時間の単位

| 単位 | 内容 | 出典 |
|---|---|---|
| ステップ | 指示を与える最小時間単位 | 【要項】 |
| 日 | 試合の進行を区切る単位。1日の活動時間をステップ数で定める | 【要項】 |

- 1試合は **4〜10日**。【要項】
- 1日のステップ数は**日ごとに異なる場合がある**。試合開始前に提供され、
  試合途中で変化することはない。【要項】【Q44】
- ステップ数は**全エージェントで共通**。【Q59】
- 各日のステップ数の範囲は **W+H 〜 (W+H)×4**（W=横幅, H=縦幅）。【Q20】
- 各日の回答時間も日ごとに定められる。最小単位は**秒**。【要項】【Q32】

## 3. マップ

### 3.1 サイズとセル番号

- マップを構成する六角形の枠を「セル」と呼び、各セルは6方向で別セルと隣接する。【要項】
- 各セルには整数値が割り当てられ、範囲は **0 〜 (縦×横 − 1)**。【要項】
- マップサイズは縦・横それぞれ **最小8セル、最大32セル**。【要項】
- セル番号は**行優先の1次元インデックス**。【設定】

```
pos = y * width + x
x   = pos % width
y   = pos / width
```

- マップは**トーラスではない**。左端→右端、上端→下端のようなラップアラウンドは
  発生しない。マップ外への移動は不正。【Q2】
- 移動できるセルは**連結**されており、エージェントが到達できない平地・山地・道路は
  存在しない。これは「**すべてのエージェントが到達可能**」という意味。【要項】【Q46】
- 各セルの地形タイプが**試合中に変化することはない**。【要項】

### 3.2 六角形の配置（座標系）

盤面は pointy-top の六角格子で、**偶数行が右に半セルずれる**形で固定されている
（even-r オフセット）。【Q1】

```
row 0:   ( 0) ( 1) ( 2) ( 3)      ← 偶数行：右に半セルずれる
row 1: ( 4) ( 5) ( 6) ( 7)
row 2:   ( 8) ( 9) (10) (11)      ← 偶数行：右に半セルずれる
row 3: (12) (13) (14) (15)
```

### 3.3 方向コードと隣接セル

行動計画で使う移動方向は、隣接6方向に割り当てられた `0`〜`5` の値。【書式】【Q47】

| コード | 0 | 1 | 2 | 3 | 4 | 5 |
|---|---|---|---|---|---|---|
| 方向 | 左上 | 右上 | 右 | 右下 | 左下 | 左 |

even-r 配置での隣接セル座標 `(row, col)` は、**行の偶奇で異なります**。

| コード | 方向 | 偶数行（右にずれる行）から | 奇数行から |
|---|---|---|---|
| 0 | 左上 | `(r-1, c)` | `(r-1, c-1)` |
| 1 | 右上 | `(r-1, c+1)` | `(r-1, c)` |
| 2 | 右 | `(r, c+1)` | `(r, c+1)` |
| 3 | 右下 | `(r+1, c+1)` | `(r+1, c)` |
| 4 | 左下 | `(r+1, c)` | `(r+1, c-1)` |
| 5 | 左 | `(r, c-1)` | `(r, c-1)` |

算出結果が盤面外に出る場合、その移動は不正です。【Q2】【書式】

## 4. 地形と移動コスト

地形タイプは「平地」「山地」「池」「道路」の4種類。【要項】
JSON上の値は次のとおり。【書式】【設定】

| JSON値 | 地形 | 移動ステップ | 消費燃料 |
|---|---|---|---|
| `0` | 平地 | 2 | 1 |
| `1` | 道路（順調） | 1 | 2 |
| `1` | 道路（混雑） | 2 | 2 |
| `1` | 道路（渋滞） | 4 | 2 |
| `2` | 山地 | 3 | 2 |
| `3` | 池 | **進入不可** | — |

（表1【要項】。道路は3状態で移動ステップが変わるが、消費燃料は状態によらず2）

> **重要**: 移動に要するステップ数・消費燃料は、いずれも
> **移動命令を受けた時点の現在地（移動元）の地形**で決まります。移動先ではありません。
> 【要項】【Q10】【Q25】

> 表1の見出し「燃量」は誤表記で、正しくは「燃料の量」（＝燃料消費量）です。【Q11】【Q28】

各地形タイプがマップ全体に占める割合の上限・下限は特に設けられていませんが、
**池・道路・山地・スポットはそれぞれ必ず1つ以上存在**します。【Q35】【Q58】

## 5. 道路の状態と交通量

### 5.1 道路の3状態

道路セルには「順調」「混雑」「渋滞」の3状態があり、**前日と前々日の2日間の交通量**に
よって決まります。【要項】

| status値 | 状態 | 移動ステップ |
|---|---|---|
| `0` | 順調 | 1 |
| `1` | 混雑 | 2 |
| `2` | 渋滞 | 4 |

- 道路の状態は**各日の開始時にサーバーから提供**され、同一日中に変化しない。【要項】
- 各日の道路の状態は**全チーム共通**。【要項】
- 各道路セルの交通量そのものは提供されず、**状態のみ**が与えられる。【Q12】

### 5.2 交通量の定義

交通量は、各道路セルにおける**全エージェントの前日と前々日の滞在ステップ数を
全チーム分合算し、チーム数で割った値**です。【要項】

```
traffic(cell) = (前日の滞在ステップ数 + 前々日の滞在ステップ数) / チーム数
```

### 5.3 日ごとの扱い

| 日 | 道路状態の決定方法 | 出典 |
|---|---|---|
| 1日目 | **すべて順調** | 【要項】 |
| 2日目 | 1日目の交通量のみで決定 | 【要項】 |
| 3日目以降 | 前日＋前々日の交通量で決定 | 【要項】 |

### 5.4 判定式

```
traffic < busyThreshold                      → 順調 (0)
busyThreshold <= traffic < jammedThreshold   → 混雑 (1)
jammedThreshold <= traffic                   → 渋滞 (2)
```
【要項】

- 混雑基準値・渋滞基準値は**試合ごとに異なる**。【要項】
- 両者とも**正の整数**。【Q30】
- 混雑基準値の範囲は **1〜5**、渋滞基準値の範囲は **2〜10**。【Q13】

### 5.5 滞在ステップ数のカウント方法

交通量の算出に用いる滞在ステップ数は、**移動後**のセルをカウントします。【Q27】

- 日の最初（0ステップ目）はアクションフェーズのみのため、**交通量はカウントされない**。【Q27】
- 日の最後は反映フェーズで**カウントされる**。【Q27】

## 6. スポット

### 6.1 基本ルール

- いくつかの**平地セル**に「スポット」が設置される。【要項】
- 巡回車がスポットに到着すると、**自動的にうどんを1玉獲得**する。【要項】
- 1巡回車が1スポットから1日に獲得できるうどんは**1玉まで**。同じ日に同じ巡回車が
  同じスポットを何度訪れても、獲得できるのは初回のみ。【要項】
- 1巡回車が獲得できるうどんの玉数に**上限はない**。【要項】
- 1セル内に配置されるスポットは**1つまで**。【Q18】【Q34】
- 各スポットの位置と系列は**同一試合中に変化しない**。【要項】

### 6.2 系列と種類

- スポットはいくつかの「系列」に分かれ、系列ごとにうどんの「種類」が異なる。【要項】
- 1つのスポットには必ず1つの系列が割り当てられる。【要項】
- 系列数の範囲は **1 〜 (マップ内のスポット数)**。【要項】
- 系列は**整数値**で与えられる（JSON上は `brand`）。【Q40】【書式】

### 6.3 在庫

- 各スポットに**最大在庫数**が定められ、在庫は**各日の開始時に最大在庫数まで補充**される。【要項】
- 最大在庫数の範囲は **1 〜 (1チームのエージェント数)**。【要項】
- 巡回車がうどんを獲得すると在庫が1玉減少する。在庫が0の場合、巡回車が到着しても
  獲得できない。【要項】
- **在庫はチームごとに独立**しており、他チームが獲得しても自チームの在庫は減らない。【要項】

### 6.4 スポット上で日をまたぐ場合

各日の0ステップ目には反映フェーズがないため、0ステップ目では獲得は行われません。
しかし**1ステップ目以降にスポットに滞在していれば獲得されます**。【Q7】

したがって、日開始時点でスポット上にいる巡回車は、**その日の1ステップ目で獲得**します。
【補足：巡回車Eの例】

待機行動でスポットのセルに留まる場合も同様で、**日が変わった後の待機であれば獲得できます**。
【Q8】【Q17】

### 6.5 同時到着

複数の巡回車が同時に同じスポットへ到着し、在庫が足りない場合は、
**マップ構成フォーマットのエージェント情報リスト内の順番（ID順）で、
若いエージェントが先に獲得**します。【Q26】

【補足】には「在庫が1のため、ID順で巡回車Bのみが獲得し、巡回車Gは獲得しない」という
具体例が示されています。

### 6.6 スポット数の範囲

スポット数の最小値は**エージェント数と同じ**、最大値は**マップの縦幅・横幅の最大値**。【Q15】

## 7. エージェント

### 7.1 共通

- 各チームは複数のエージェントを管理する。【要項】
- エージェント数は **3〜8体**。これは**1チームあたり**の数。【要項】【Q50】
- 初期位置はあらかじめ指定され、**スポットが設置されていない平地**が指定される。【要項】
- 初期位置は**すべて異なるセル**。【Q37】
- 初期位置は**全チームで共通**。【Q38】
- 試合中はマップ構成フォーマットの `agents` リストの順序がエージェントに割り当てられ、
  試合情報・種別回答・行動計画のすべてが**同じ順序**で記述される。【書式】

### 7.2 種別

エージェントには2種類のタイプがある。【要項】

| kind値 | 種別 | 役割 |
|---|---|---|
| `0` | 巡回車 | スポットを巡ってうどんを獲得する。移動時に燃料を消費する |
| `1` | 補給車 | 巡回車に燃料を供給する。うどんは獲得できない |

- プレイヤーは**試合開始時に各エージェントのタイプを指定**する。指定したタイプは
  試合終了まで変更できない。【要項】
- 巡回車では燃料を供給できず、補給車ではうどんを獲得できない。【要項】

### 7.3 巡回車

- 移動時に、移動命令を受けた時点での地形に応じた燃料を消費する。【要項】
- 積載できる燃料に上限があり、**全チームの全巡回車に同じ上限**が定められる。【要項】【Q51】
- 燃料が不足している場合、**燃料が補給されるまで待機しなければならない**。【要項】
- 自分で燃料を補給することはできない。【要項】

### 7.4 補給車

- 燃料の**最大積載量は設定されておらず、無限に燃料を供給できる**。【要項】
- **燃料を使わずに**別セルに移動できる。【要項】
- うどんは獲得できない。【要項】

## 8. 移動

### 8.1 基本ルール

- エージェントは**6方向に隣接するセル**に移動できる。【要項】
- **他のエージェントが滞在しているセルにも移動可能**。【要項】
- 指定のステップ数だけ移動せずその場に「待機」する命令も与えられる。【要項】
- 移動命令を受けたエージェントは、**現在地の地形に割り当てられたステップ数の経過後**に
  次のセルへ移動する。【要項】

```
現在地の地形 → 移動時間・燃料消費量が決定 → その時間の経過後に隣接セルへ到着
```

- 移動命令を出してから移動が完了するまでの間に、別の移動命令を出すことはできない。
  回答は1日の全ステップの行動をすべて指定する形で提出するため。【Q23】【Q24】

### 8.2 待機

行動計画の **`-1` 以下の値**が待機を表し、**絶対値がステップ数**になります。【書式】

| 値 | 意味 |
|---|---|
| `-1` | 1ステップ待機 |
| `-3` | 3ステップ待機 |
| `-15` | 15ステップ待機 |

- 待機命令は**待機するステップ数を指定**するもので、**セルの地形には影響されない**。【Q49】
- 待機中は**燃料を消費しない**。【Q16】

## 9. 燃料と補給

### 9.1 燃料上限

- 巡回車が搭載可能な燃料の上限は、**1日目のステップ数の1〜3倍**。【Q14】
- これは整数倍（1倍・2倍・3倍）ではなく、**1〜3倍の範囲内**で設定される。【Q60】
- 燃料積載量の上限は**正の整数**。【Q31】
- 各地形セルの移動に必要な燃料消費量より上限が小さいことはない。【Q36】
- 1日目の巡回車の燃料積載量は**上限と同じ値**。【要項】
- 2日目以降は**前日終了時点の積載量**を引き継ぐ。前日終了時点の残り燃料は
  各日の試合情報フォーマットの `fuel` キーに与えられる。【要項】【Q19】

> フォーマット資料の例にある `"daySteps": [50, 100, 150, 200]` に対する
> `"fuelLimits": 20` は**サンプル上の誤り**です。daySteps が 50 の場合、
> fuelLimits は 50〜150 の範囲となります。【Q62】

### 9.2 補給

- 補給車が巡回車と**同じセルに1ステップ以上いた場合**、巡回車の燃料は自動的に
  最大積載量まで補給される。【要項】
- 「同じセルに1ステップ以上いた場合」とは、**反映フェーズの「1.4 燃料の補給」の
  タイミングで同じセルにいた場合**を指す。【Q22】

補給の成否は移動の反映順序に依存するため、以下の区別が重要です。【Q22】

| ケース | 結果 |
|---|---|
| 巡回車と補給車が**同じセルから同じセルへ**一緒に移動 | 補給される（【補足】巡回車E と補給車A） |
| 補給車のいたセルへ巡回車が**追いかけて**移動（1セル後ろを追走） | **補給されない**。補給車の移動反映が先に行われ、補給時には別セルになるため（【補足】巡回車F と補給車A） |
| **その日の最後のステップ**で同じセルに移動 | 補給される。移動の後に補給が行われるため |

また、燃料の消費は各ステップの補給**より前**に行われるため、
あるステップで補給された燃料を使えるのは**次のステップからの移動命令**です。【Q22】【Q48】

巡回車と補給車が同じセルから同じセルへ移動する場合（くっついて移動する場合）、
反映フェーズの最初に燃料を消費し、その後に補給が行われるため、
**ステップ終了時点では燃料は減少していません**。【Q48】

## 10. 1日の処理（フェーズ）

### 10.1 フェーズの種類

1日のステップ数を N とすると、処理は次の2フェーズで構成されます。【Q6】【補足】

**1. 反映フェーズ（0ステップ目は処理なし）**

以下の順序で処理されます。**この順序は変更されません**。

```
1.1. 燃料の消費
1.2. 移動の反映
1.3. うどんの獲得（現在地がスポットであれば）
1.4. 燃料の補給（補給車と巡回車が同一セルにいれば）
1.5. 交通量の更新
```

**2. アクションフェーズ（最終ステップは処理なし）**

次のアクション（移動 or 待機）の反映を予約します。
移動を予約した時点では燃料を消費せず、**燃料消費は次の反映フェーズで行われます**。

### 10.2 フェーズの流れ

```
0 step.      : アクションフェーズ
1 step.      : 反映フェーズ → アクションフェーズ
...
N-1 step.    : 反映フェーズ → アクションフェーズ
N (最終) step.: 反映フェーズ
```

つまり **0ステップ目には反映がなく、最終ステップにはアクションがありません**。【Q6】【補足】

> 移動の可否判定は**回答受付時**に行われているため、各ステップの処理では
> すべての移動が可能である前提で進行します。【Q6】

### 10.3 日の終了と翌日への引き継ぎ

その日の最終反映フェーズが終わった状態が翌日の基準になります。【要項】

| 項目 | 翌日の値 | 出典 |
|---|---|---|
| エージェント位置 | 前日終了時点の位置 | 【要項】 |
| 巡回車の燃料 | 前日終了時点の積載量 | 【要項】 |
| スポット在庫 | **最大在庫数まで補充** | 【要項】 |
| 道路状態 | 前日・前々日の交通量から決定 | 【要項】 |

ある日の回答時間が終了してから翌日の状態が配布されるまでに、実況や解説を行う時間などは
**設けられません**。即座に翌日の回答時間が開始されます。【Q54】

## 11. 回答フォーマット

### 11.1 エージェント種別の回答

試合開始前に、エージェントの種類を JSON 配列で提出します。【書式】

```json
[0, 1, 0, 1]
```

- `0`=巡回車、`1`=補給車
- 配列の**要素数はエージェント数と一致する必要**がある
- 要素数が異なる、または `{0, 1}` 以外が指定されているデータは不正としてリジェクト

**制限時間内に正しいデータが受理されなかった場合、すべてのエージェントが巡回車**に
なります。【書式】【Q53】

### 11.2 行動計画の回答

各日の行動計画を、全エージェント分の行動データを含む JSON 配列で提出します。【書式】

```json
[
  [-15],
  [0, 1, -10]
]
```

- 外側の配列＝エージェント（`agents` と同じ順序）、内側＝そのエージェントの行動列
- `-1` 以下＝待機（絶対値がステップ数）
- `0`〜`5`＝移動方向

例の `[0, 1, -10]` は「左上に移動 → 右上に移動 → 10ステップ待機」を意味します。【書式】

**各エージェントの行動計画は1日のステップ数と一致する必要があります。**【書式】

---

## 12. 無効な回答（リジェクト条件）

回答受付時に、行動のステップ数の判定と移動の可否の判定が行われます。【Q6】

以下は不正であり、**回答全体がリジェクト**されます。

| 不正条件 | 出典 |
|---|---|
| 行動計画が規定ステップ数と一致しない（超過・不足） | 【書式】【Q6】 |
| 池への移動 | 【要項】【書式】 |
| マップ外への移動 | 【要項】【書式】 |
| 隣接していないセルへの移動 | 【要項】 |
| **燃料が不足する移動** | 【要項】【Q6】 |
| 移動に要するステップ数が不足しているのに移動を命令 | 【要項】【Q6】 |
| 種別の要素数不一致 / `{0,1}` 以外の値 | 【書式】 |

> **1エージェントでも行動計画が不正な場合、すべてのエージェントの行動計画を不正とし、
> リジェクトします。**【書式】部分採用はされません。

### 12.1 特に注意すべき点

**1日の終盤で移動に要するステップ数が不足する場合は、最後に待機を指定して
既定のステップ数と一致させてください。**【Q6】

【補足】には以下の具体例が示されています。

- **巡回車A**: セル3に到達しているが1日のステップが残っているので、
  最後に待機を指定しないとエラーになる
- **巡回車B**: セル3に到達したステップで1日が終了するのでそのままで完了
- **巡回車C**: 到達までにステップ数が不足しているので、移動を指定するとエラーになる
- **巡回車D**: 燃料積載量が移動に必要な量を下回るので、その後に移動を指定するとエラーになる
- **巡回車F**: セル1まで移動した時点で燃料が移動に必要な量を下回っているので、
  その後に移動を指定するとエラーになる

### 12.2 有効な回答が間に合わない場合

回答時間内に有効な回答を送れなかった場合、
**各エージェントは前日終了時（初日なら初期位置）のセルで、最終ステップまで待機**
となります。【書式】【Q55】

その日を丸ごと失うことになるため、致命的です。

### 12.3 再提出

- 制限時間内であれば**再提出が可能**。【要項】
- ただし、**試合の進行を妨げるほどの回数や容量を送信すると妨害行為とみなし
  失格となる可能性**がある。【要項】
- **最後に受理された有効な回答を採用**する。【要項】
- 回答がサーバーで受理されると、有効または無効（フォーマットエラー）が通知される。【要項】

## 13. 試合の進行

【要項】に示された進行手順は以下のとおりです。

1. 試合開始前にマップ構成が提供され、プレイヤーは各エージェントのタイプを指定する
2. 試合開始とともに、全チームのエージェント選択情報を含むマップ情報がサーバーから提供される
3. 1日目の回答時間内に、プレイヤーは1日目の行動を提出する
4. 1日目の回答時間終了後、1日目終了時の全チームのエージェント位置と渋滞情報を反映した
   2日目のマップ情報がサーバーから提供される
5. 2日目以降も同様に、プレイヤーは各日の回答時間内に行動を提出する
6. 指定された日数分、この手順を繰り返す

マップ情報の更新に若干のタイムラグが発生する場合があります。【要項】

### 13.1 試合開始前のマップ構成フォーマット

【書式】

| キー | 内容 |
|---|---|
| `startsAt` | 試合の開始時刻（UNIX TIME） |
| `daySeconds` | 各日の回答時間の秒数 |
| `daySteps` | 各日のステップ数。**配列の要素数が日数を表す** |
| `map.height` / `map.width` | マップの縦幅 / 横幅 |
| `map.cells` | 各セルの地形タイプ（0:平地 1:道路 2:山地 3:池） |
| `spots[].brand` / `.pos` / `.stocks` | スポットの系列 / 位置 / 最大在庫数 |
| `agents[]` | 自プレイヤーのエージェント初期位置 |
| `fuelLimits` | 燃料積載量上限 |
| `players` | 参加プレイヤー数 |
| `busyThreshold` / `jammedThreshold` | 混雑基準値 / 渋滞基準値 |

### 13.2 各日開始時の試合情報フォーマット

【書式】

| キー | 内容 |
|---|---|
| `endsAt` | 当該日の回答受付終了時刻（UNIX TIME） |
| `day` | 日付。**初日は 0** |
| `agents[]` | 自チームのエージェント情報 `{kind, pos, fuel}` |
| `others[]` | 他チームのエージェント情報 `{id, agents[]}` |
| `traffics[]` | 道路セルの状態 `{pos, status}`（0:順調 1:混雑 2:渋滞） |

- 他チームについては、**各日の最終ステップでのエージェントの位置や燃料積載量**が
  記載される。【Q39】
- 1日目（Day 1）でも2日目以降と同様に各エージェントの位置や燃料などのパラメータが
  与えられる。【Q61】

## 14. 勝敗判定

うどんの種類数、玉数、回答時間により、以下の優先順位で勝敗を決定します。【要項】

| 順位 | 判定基準 | 勝者 |
|---|---|---|
| ① | 1試合で獲得したうどんの**種類数** | 多いチーム |
| ② | 各日に獲得したうどんの**種類数の累積**（日ごとの種類数の合計） | 多いチーム |
| ③ | 1試合で獲得したうどんの**玉数の総和** | 多いチーム |
| ④ | 各日の最後に送信した有効な回答の**回答時間の累積** | 少ないチーム |
| ⑤ | サイコロなどで勝敗を決めるか引き分け | — |

回答時間は「各日の最後の有効な回答が送られるまでに要した時間を合計した値」で
判定されます。【Q56】

> **戦略上の含意**: ②の基準があるため、同じ種類数を揃えるのでも
> **早い日に多くの種類を揃えるほど累積が伸びます**。
> 最終日に全種類を揃えても、累積には1日分しか計上されません。

## 15. 通信仕様

- 競技ブースの**有線LAN**に各チームのPCを接続し、**HTTP の POST・GET** 形式で
  データを送受信する。【要項】
- **HTTP/1.1 のみ対応**。HTTP/3 のリクエストは受け付けない。【Q41】
- リクエスト頻度は**秒間5リクエストほど**を目安とする。【Q42】
- サーバーの時計は **NICT の NTP** で同期されている。【Q57】
- Wi-Fi による通信は認められない（持ち込み機器間の Bluetooth 等は可）。【要項】

### 15.1 API エンドポイント

【API】（Procon 37 API, OpenAPI 3.1.0）

| メソッド/パス | 内容 |
|---|---|
| `GET /setting` | 試合設定（MatchSetting）を取得 |
| `GET /` | 試合状態（MatchState）を取得 |
| `POST /agent` | エージェント種別を提出 |
| `POST /` | 行動計画を提出。レスポンスの `revision` が0未満なら提出失敗 |

認証は **`Procon-Token` ヘッダ**、または **`token` クエリパラメータ**でトークンを渡します。【API】

同じ日に複数回提出でき、`revision` が大きいものがより後に受理された提出です。【API】

### 15.2 動作確認用の簡易サーバー

公式から競技者向けの動作確認サーバー（`procon-server`）が提供されています。【簡易】

| フラグ | デフォルト | 説明 |
|---|---|---|
| `-config` | （必須） | 問題・参加チーム情報を含む設定JSONのパス |
| `-addr` | `PORT` 環境変数、未設定時は `:8080` | HTTPリッスンアドレス |
| `-kind-deadline` | `5s` | 起動からエージェント種別締切までの時間 |
| `-match-start-delay` | `5s` | 種別締切から試合開始までの時間 |

> **注意**: これは**動作確認用サーバーの起動設定**です。デフォルトの `5s` を
> 本番競技の種別決定時間・試合開始時間と混同しないでください。
> 本番では、エージェントのタイプ指定の解答時間は**1分程度**、日毎の解答時間も
> **1分程度**が想定されています（詳細は本選実施要項で連絡）。【Q4】【Q5】【Q52】

## 付録: 公式の状態遷移例

【補足】に、実際の状態遷移を追える具体例が掲載されています。
シミュレーターの統合テストには、この公式例をそのまま使うのが最も確実です。

### 設定

```
セル: 0 ─ 1 ─ 2 ─ 3  （一直線に隣接）
```

- セル0・1 は**道路**。セル0は順調（1ステップ・燃料2）、セル1は混雑（2ステップ・燃料2）
- セル2・3 は**平地**（2ステップ・燃料1）
- セル2には**在庫4のスポット**がある
- 巡回車の最大燃料積載量は **3**
- 1日のステップ数は **6**（0〜6ステップ）

### 初期配置と行動計画

| エージェント | 初期セル | 行動計画 | 参考 |
|---|---|---|---|
| 巡回車A | 0 | `2, 2, 2, -1` | RT, RT, RT, WT(1) |
| 巡回車B | 0 | `-1, 2, 2, 2` | WT(1), RT, RT, RT |
| 巡回車C | 0 | `-2, 2, 2, -1` | WT(2), RT, RT, WT(1) |
| 巡回車D | 0 | `-3, 2, -2` | WT(3), RT, WT(2) |
| 巡回車E | 2 | `5, 5, -2` | LF, LF, WT(2) |
| 巡回車F | 3 | `5, 5, -2` | LF, LF, WT(2) |
| 巡回車G | 3 | `-2, 5, 5` | WT(2), LF, LF |
| 補給車A | 2 | `5, 5, -2` | LF, LF, WT(2) |

（`2`=右移動、`5`=左移動、`-3`〜`-1`=待機）

### 各エージェントの留意点

- **巡回車A**: セル3に到達しているが1日のステップが残っているので、
  最後に待機を指定しないとエラーになる
- **巡回車B**: セル3に到達したステップで1日が終了するのでそのままで完了
- **巡回車C**: セル3に到達していないが到達までにステップ数が不足しているので、
  移動を指定するとエラーになる。スポット（セル2）に到達しているが、
  **在庫がなくなっているのでうどんは獲得できない**
- **巡回車D**: 燃料積載量が移動に必要な量を下回るので、その後に移動を指定するとエラーになる
- **巡回車E**: **スポットからのスタートなのでステップ1でうどんを獲得する**。
  補給車と同時に移動するので燃料は常に最大積載量となる
- **巡回車F**: 常に補給車の1セル後ろを移動するので、**補給が行われない**。
  セル1まで移動した時点で燃料が移動に必要な量を下回っている
- **巡回車G**: スポットに移動するが、巡回車Bと同じタイミングで移動し、
  この時点で在庫が1のため、**ID順で巡回車Bのみが獲得**し、巡回車Gは獲得しない
